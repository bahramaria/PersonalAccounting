# 08 — نقشه راه (نسخه ۲)

> بازنویسی بر پایه `10-market-insights.md`: پیامک، چک، اقساط و بدهی/طلب جلو آمدند؛ چندارزی در دهک ۸ قرار گرفت و OCR، Sync و Workspace خارج از دامنه نسخه فعلی ماندند.

## فاز ۰ — Spikeها (۲ هفته؛ فقط ۵ مورد حیاتی)
| Spike | سؤال | معیار قبول |
|---|---|---|
| S1 | EF Core + SQLite3MC با cipher سازگار SQLCipher v4 روی Targetهای فعلی Android/Windows | CRUD + بازکردن با کلید + مهاجرت داده + CI دو پلتفرم سبز؛ Runtime واقعی هنوز لازم است |
| S2 | RTL در MAUI: Shell، CollectionView، Entry مبلغ، نمودار | اسکرین‌شات‌های تأییدشده + فهرست Workaround |
| S3 | درستی تقویم شمسی .NET | تأیید شد؛ تطابق روزبه‌روز ۱۲۰۰–۱۵۰۰ با مرجع Borkowski در ۱۰۹٬۹۳۸ روز |
| **S4** | **پیامک Android:** طراحی و پیاده‌سازی خواندن/دریافت، سیاست مجوز، مدیریت خطا و تست‌های خودکار مسیرهای ورود | صحت پیاده‌سازی و تست‌های خودکار در CI؛ آزمون عملی روی دستگاه واقعی، مسیرهای ورود و تفاوت رفتار OEMها به ارزیابی پس از تکمیل محصول منتقل شد |
| S5 | یادآور: اعلان محلی روی Android/iOS در برندهای سخت‌گیر | اعلان در زمان درست؛ راهنمای باتری |
*(Spike OCR، PDF و بیومتریک حذف/موکول شد؛ PDF و OCR در ۱٫۱ و بعد.)*

**دامنه پلتفرم S1:** پروژه در حال حاضر فقط Targetهای Android و Windows دارد؛ iOS تا زمان اضافه‌شدن Target و CI مستقل، بخشی از معیار پذیرش نسخه فعلی نیست.

## فاز ۱ — هسته (نسخه داخلی ۰٫۱)
Solution، تست‌های Core، Domain (`Money`, Ledger)، Localization (شمسی/ارقام)، حساب/دسته/تراکنش، Quick-add، جستجو، داشبورد، قفل، بکاپ، RTL و تم. در این مرحله Shell MAUI برای Android/Windows و چرخه آغاز دیتابیس EF Core SQLite نیز اسکلت‌بندی شده‌اند؛ این مورد به‌معنی تأیید رمزنگاری یا RTL روی دستگاه نیست.

## فاز ۲ — «ویژگی‌های قهرمان» (نسخه ۰٫۵ بتا)
ثبت از پیامک + صف تأیید + تطبیق موجود، دفتر بدهی/طلب، چک (وضعیت/بایگانی/یادآور)، وام و اقساط، یادآورها.

## فاز ۳ — نسخه ۱٫۰ (انتشار در بازار/مایکت)
گزارش‌ها و نمودارها، خروجی Excel/CSV، بکاپ خودکار و انتقال گوشی، Onboarding، بهینه‌سازی، تست RTL روی دستگاه‌های واقعی، **بتای بسته با ۲۰–۵۰ کاربر واقعی**. آزمون میدانی پیامک روی دستگاه‌ها در گیت پس از تکمیل کل محصول انجام می‌شود.

## نسخه ۱٫۱
الگوهای پیشرفته تکرارشونده، پیوست رسید، PDF و Split تراکنش.

## نسخه ۱٫۲
Windows، حساب کاربری + Sync، Pro (آزمون رایگان بلند)، پرداخت (بازار/درگاه) — هرکدام پس از تأیید تقاضا.

## بعداً (در صورت تقاضای واقعی)
OCR، دارایی‌ها (طلا/دلار)، E2EE، چندکاربره، AI/دسته‌بندی هوشمند، بازار جهانی.

## روش اجرایی مصوب: توسعه Feature Batch

فازهای محصول بالا مرجع دامنه و ترتیب انتشار باقی می‌مانند؛ برای اجرای روزمره، هر فاز به چند **بسته قابلیت کامل (Feature Batch)** شکسته می‌شود. هدف هر بسته تحویل یک بخش منسجم، قابل استفاده و قابل ارزیابی از محصول است، نه صرفاً افزودن چند کلاس یا لایه فنی.

قواعد الزام‌آور اجرای بسته‌ها:

1. هر بسته باید نتیجه قابل مشاهده و قابل استفاده برای کاربر داشته باشد و معیار پذیرش آن پیش از شروع روشن باشد.
2. بسته، تمام بخش‌های لازم همان قابلیت را یکجا پوشش می‌دهد: مدل دامنه، منطق و سرویس Application، ذخیره‌سازی و Migration در صورت نیاز، رابط کاربری و ViewModel، منابع فارسی/انگلیسی و RTL، و تست‌های متناسب.
3. تغییرات مرتبط در قالب یک یا چند Commit منطقی تحویل می‌شوند؛ از خردکردن کار به Commitهای لایه‌ای و بی‌نتیجه پرهیز می‌شود.
4. در پایان هر بسته، تست‌های مرتبط و CI موجود برای پلتفرم‌های هدف باید سبز باشند. قابلیت ناقص یا صرفاً اسکلت‌بندی‌شده، تکمیل‌شده محسوب نمی‌شود.
5. بسته‌ها باید محدود و مستقل از نظر اعتبارسنجی باشند؛ بزرگ‌تر شدن گام‌ها مجوز حذف تست، نادیده‌گرفتن ریسک یا عبور از گیت پذیرش نیست.
6. گیت‌های فاز صفر، به‌ویژه S1 رمزنگاری و S2 اعتبارسنجی RTL، همچنان مستقل و لازم‌الاجرا هستند. تا زمان عبور از هر گیت، محدودیت آن باید صریح باقی بماند و نباید قابلیت یا تضمین تأییدنشده اعلام شود.
7. ترتیب بسته‌ها می‌تواند در جزئیات اجرایی با وابستگی‌های واقعی تنظیم شود، اما دامنه، تصمیم‌های ثبت‌شده و ترتیب کلان فازهای محصول بدون تصمیم مستند جدید تغییر نمی‌کنند.

## دهک‌بندی مصوب کل محصول

مخرج پیشرفت، کل محصول حسابیار در مسیر تکامل آن است؛ نسخه ۱٫۰ یک نقطه انتشار است، نه پایان محصول. دهک‌ها بر اساس قابلیت قابل استفاده و معیار پذیرش سنجیده می‌شوند:

| دهک | محدوده محصول | خروجی قابل تحویل |
|---|---|---|
| ۱ ـ ۱۰٪ | هسته حسابداری | حساب‌ها، دسته‌ها، دفتر کل، دریافت، پرداخت، انتقال و قواعد صحت مالی |
| ۲ ـ ۲۰٪ | تجربه اصلی استفاده | ثبت سریع، جستجو، فیلتر، ویرایش و مدیریت تراکنش‌ها، داشبورد، تنظیمات پایه و Onboarding |
| ۳ ـ ۳۰٪ | مدیریت تعهدات مالی | اشخاص، بدهی و طلب، چک، وام و اقساط، محاسبه مانده و گردش مالی |
| ۴ ـ ۴۰٪ | ورود هوشمند اطلاعات | ورود پیامک، قواعد تفسیر بانک‌ها، صف تأیید، تشخیص تکراری و تطبیق موجودی |
| ۵ ـ ۵۰٪ | زمان‌بندی و جریان مالی | اعلان‌های سیستم‌عامل، یادآورها و تراکنش‌های تکرارشونده |
| ۶ ـ ۶۰٪ | گزارش‌گیری و تحلیل | گزارش‌های مالی، نمودارها، گزارش اشخاص و خروجی Excel/CSV/PDF |
| ۷ ـ ۷۰٪ | امنیت و نگهداری داده | رمزنگاری پایگاه داده، قفل PIN/بیومتریک، بکاپ، بازیابی و انتقال؛ پیوست اسناد در نسخه ۱٫۱ |
| ۸ ـ ۸۰٪ | قابلیت‌های توسعه‌یافته مالی | بودجه‌بندی، برچسب، دوره مالی، شماره‌گذاری اسناد، روش‌های پیشرفته وام و چندارزی |
| ۹ ـ ۹۰٪ | محصول چنددستگاهی و تجاری | حساب کاربری، همگام‌سازی، چنددستگاهی، Pro و پرداخت |
| ۱۰ ـ ۱۰۰٪ | قابلیت‌های پیشرفته و بلوغ محصول | OCR، دارایی‌ها، دسته‌بندی هوشمند، AI، چندکاربره، E2EE و آمادگی بازار گسترده‌تر |

قواعد سنجش:
1. هر دهک دقیقاً ۱۰ واحد درصد از دامنه کل محصول را نمایندگی می‌کند؛ وزن‌ها به نسخه ۱٫۰ محدود نیستند.
2. تکمیل دهک منوط به تحویل تجربه قابل استفاده، منطق، ذخیره‌سازی، UI، localization، تست و معیارهای پذیرش همان محدوده است.
3. کار زیرساختی به‌تنهایی پیشرفت محصول محسوب نمی‌شود.
4. قابلیت وابسته به دستگاه یا سرویس خارجی تا زمان آزمون واقعی، تکمیل قطعی محسوب نمی‌شود.
5. اگر یک قابلیت در چند دهک سهم دارد، سهم و معیارهای پذیرش آن باید پیش از شروع در همین سند مشخص شود.
6. نسخه‌های ۱٫۰، ۱٫۱ و ۱٫۲ نقاط انتشار در طول این مسیرند؛ اتمام هر نسخه به معنی اتمام دهک‌بندی کل محصول نیست.

### وضعیت فعلی بر مبنای دهک‌بندی کل محصول

- دهک ۱ و ۲: قابلیت‌های اصلی حسابداری و تجربه روزمره در شاخه پیاده‌سازی شده‌اند؛ برخی معیارهای کارایی و اعتبارسنجی میدانی همچنان گیت انتشار هستند.
- دهک ۳: دفتر اشخاص و بدهی/طلب، چک، وام و اقساط در کد پیاده‌سازی شده‌اند و CI شاخه سبز است. آزمون واقعی مهاجرت و بازبینی RTL روی دستگاه همچنان گیت انتشار است.
- دهک ۴: پیاده‌سازی نرم‌افزاری گسترده شده و در انتظار عبور از گیت‌های CI و بازبینی نرم‌افزاری نهایی است. هسته تفسیر، صف پایدار پیامک، جلوگیری از تکراری، ورود Paste/Share، دریافت خودکار پیامک جدید با مجوز اختیاری RECEIVE_SMS، مرور/ویرایش/نادیده‌گرفتن، تأیید دستی، هشدار تراکنش دستی مشابه، تبدیل واحد صریح تومان به ریال و تطبیق موجودی با Adjustment دوطرفه و متوازن پیاده‌سازی شده‌اند. تأیید گروهی پیام‌های هم‌نوع در یک تراکنش پایگاه داده اتمیک انجام می‌شود و در صورت نامعتبر بودن حتی یک مورد، کل دسته Rollback می‌شود. حافظه پیشنهاد دسته بر اساس فرستنده/بانک و نوع تراکنش پس از تأیید موفق روی همان دستگاه ذخیره می‌شود و صرفاً پیشنهاد است، نه ثبت خودکار. قواعد بانک‌ها از کاتالوگ JSON داخلی بارگذاری می‌شوند؛ اعتبارسنجی کلیدهای تکراری، مقادیر و Regex و محدودیت زمان اجرای Regex پیاده‌سازی شده است. مبالغ با جداکننده هزارگان فقط در قالب معتبر پذیرفته می‌شوند و قالب اعشاری/مبهم به بررسی دستی می‌رود. هویت پیام‌های دریافتی Android از زمان دریافت پیام ساخته می‌شود تا تحویل دوباره همان SMS تکراری بماند، اما دو تراکنش واقعی با متن و مبلغ یکسان در زمان‌های متفاوت با هم اشتباه نشوند. تطبیق موجودی نیز در صورت وجود گردش بانکی با تاریخ بعدتر متوقف می‌شود تا موجودی یک پیام تاریخی با مانده فعلی اشتباه مقایسه و Adjustment نادرست ساخته نشود. تست‌های یکپارچه برای تأیید گروهی و Rollback، تشخیص تکراری مبتنی بر زمان و جلوگیری از تطبیق تاریخی اضافه شده‌اند. قالب بانک پارسیان با ۷ نمونه تراکنش واقعی (۶ برداشت و ۱ واریز) به‌عنوان Rule اولیه پوشش داده شده؛ پیام‌های دارای رمز تأیید از صف مالی حذف می‌شوند و خرید قبضینو دارای Code به‌دلیل احتمال کد پیگیری برای بررسی دستی نگه داشته می‌شود. واحد مبالغ نمونه‌های پارسیان ریال است و Rule ضریب ۱ دارد. تاریخ کوتاه MM/DD بدون سال حفظ می‌شود و تاریخ آن حدس زده نمی‌شود. ورود تاریخچه Android با رضایت صریح، مجوز READ_SMS و محدودیت ۵۰۰ پیام از ۹۰ روز اخیر انجام می‌شود؛ فقط پیام‌های مالی/نیازمند بررسی به صف می‌روند. مجوزهای SMS برای انتشار در Google Play مشمول محدودیت‌های سیاستی‌اند و مسیر توزیع باید پیش از انتشار بررسی شود. موارد باز پیش از اعلام تکمیل دهک: تکمیل تست‌های خودکار و بررسی UX، localization و RTL در سطح کد و CI. آزمون عملی دریافت خودکار پیامک روی دستگاه واقعی و OEMهای مختلف و آزمون میدانی مسیرهای ورود Android به گیت پس از تکمیل کل محصول منتقل شده‌اند. تعیین بانک‌های هدف، گردآوری corpus شامل حداقل ۵۰ پیامک از ۵ بانک و سنجش دقت تفسیر ≥۹۵٪ از گیت تکمیل دهک خارج شده و به مرحله ارزیابی کیفیت پس از تکمیل کل محصول منتقل شده است. گزینه ثبت خودکار تا اعتبارسنجی Ruleهای واقعی فعال نمی‌شود. معیار آماری ۵۰ پیامک از ۵ بانک و دقت ≥۹۵٪ مانع تکمیل دهک چهارم نیست و پس از تکمیل کل محصول اجرا خواهد شد. سایر معیارهای عملکردی و تست‌های خودکار که برای اطمینان از صحت پیاده‌سازی لازم‌اند، همچنان در گیت تکمیل دهک باقی می‌مانند.
- دهک ۵: تکمیل شد؛ پیاده‌سازی نرم‌افزاری یادآورها، اعلان‌های زمان‌بندی‌شده Android/Windows و تراکنش‌های تکرارشونده انجام شد و CI شامل تست‌های Core و Build هر دو پلتفرم سبز است. آزمون دستگاه واقعی و رفتار OEM مطابق تصمیم محصول به گیت پس از تکمیل محصول منتقل شده است.
- دهک ۶: تکمیل شد؛ گزارش‌های مالی، روند ماهانه شمسی، تراز حساب‌ها، ارزش خالص دارایی، مانده اشخاص و خروجی Excel/CSV پیاده‌سازی شدند و CI سبز است.
- دهک ۷: تکمیل شد؛ رمزنگاری پایگاه داده، قفل PIN و محدودیت تلاش، ورود بیومتریک بومی Android/Windows، بکاپ رمزنگاری‌شده، بازیابی و انتقال پیاده‌سازی شدند و CI شامل تست Core و Build هر دو پلتفرم سبز است. پیوست اسناد طبق F9 به نسخه ۱٫۱ موکول است؛ اعتبارسنجی Runtime رمزنگاری روی دستگاه واقعی همچنان گیت انتشار باقی می‌ماند.
- دهک ۸: تکمیل شد؛ بودجه چندارزی، برچسب و اتصال تراکنش، دوره مالی و شماره سند یکتا، تبدیل ارز، وام و اقساط هم‌ارز، دفتر اشخاص و چک چندارزی، دقت واحد خرد ارزها، نمایش و ورود اعشاری و خروجی Excel/CSV با مقیاس صحیح پیاده‌سازی و با CI سبز اعتبارسنجی شدند.
- دهک‌های ۹ و ۱۰: در انتظار اجرا.

- Refresh Token تصادفی ۵۱۲ بیتی تولید می‌شود؛ فقط SHA-256 آن در SQL Server ذخیره می‌شود.
- هر نشست به کاربر و شناسه دستگاه متصل است و نام دستگاه با طول محدود نگهداری می‌شود.
- عمر Refresh Token برابر ۳۰ روز است؛ Access Token همچنان ۱۵ دقیقه اعتبار دارد.
- Endpoint ورود OTP پس از اعتبارسنجی دستگاه، نشست اولیه را ایجاد و هر دو Token را برمی‌گرداند.
- Endpoint تازه‌سازی، Refresh Token را در تراکنش Serializable به‌صورت چرخشی تعویض می‌کند؛ استفاده مجدد از Token باطل‌شده باعث ابطال نشست‌های فعال همان خانواده می‌شود.
- Endpoint خروج، نشست همان دستگاه را باطل می‌کند.
- Migration افزایشی SQL Server و آزمون‌های مدل EF برای Hash یکتا، رابطه کاربر و ایندکس‌های دستگاه/خانواده اضافه شده‌اند.
- این بسته هنوز گیت CI و تست رفتاری چرخش هم‌زمان/تشخیص Replay را نگذرانده است؛ فهرست و ابطال نشست سایر دستگاه‌ها و احراز هویت/اعتبارسنجی Access Token همچنان باز هستند.
